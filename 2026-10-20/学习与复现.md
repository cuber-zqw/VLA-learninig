`joint_drive.npz` 中 `qpos` 是实际关节位置，`target` 是单个关节 fl_joint1 的目标弧度，`time` 是仿真步结束时间。将二者比较可以理解“给目标”和“已到达”之间的差别。视频每 10 个 1/250 秒物理步保存一帧，以 25 fps 编码，4 秒仿真对应 4 秒视频。

机器人全身有 38 个活动关节，不等于任务动作有 38 维。任务只控制前方双臂与夹爪，其动作向量是 6+1+6+1 共 14 维；实际字段须再看生成的数据。

## 专家任务代码怎么读

按顺序打开：

- `RoboTwin/envs/stack_blocks_two.py` 的 `load_actors()`：生成边长 0.05 m 的红、绿方块，随机放置。
- `play_once()` / `pick_and_place_block()`：按 x 位置选左/右臂，抓取、抬起、放置，再移开夹爪。
- `RoboTwin/envs/robot/planner.py` 的 `CuroboPlanner`：将世界目标变换到规划器基坐标，求解关节路径。
- `RoboTwin/envs/_base_task.py` 的 `take_dense_action()`：逐步设置控制目标并推进物理。
- `check_success()`：绿色方块相对红色方块中心的目标偏移为 `[0, 0, 0.05]` m，各轴误差必须小于 `[0.025, 0.025, 0.012]` m，并要求双夹爪打开。

专家会读取方块真实位姿，因此这条链路并不是视觉策略推理。生成示范后，才能讨论如何让策略根据相机图像预测动作。

## 读数据时特别注意

该固定版本 `_base_task.get_obs()` 将 `Robot.get_left_arm_jointState()` 等函数写入 `joint_action`。继续读 `robot.py` 可见，6 个机械臂值来自 `joint.get_drive_target()`，不是 `get_qpos()`。不要因函数名带 jointState 或配置写 qpos 就把它当作实测关节位置。

- `joint_action/vector`：左右臂关节控制目标和夹爪命令，本次实际 `(325, 14)`。
- `endpose/left_endpose`、`right_endpose`：由实际机器人位姿和末端偏移计算，包含位置与四元数；具体定义见 `get_arm_pose()` 和 `_trans_endpose()`。
- `observation/.../rgb`：上游以 JPEG 字节存储，不能将 HDF5 形状直接当成 `(T,H,W,3)`。
- 单位和坐标系要从写入与转换代码确认，不能只凭字段名猜。

物理步长为 1/250 秒。默认每段运动间隔 15 步采样，同时在运动边界额外采样；文件不提供精确逐行时间戳。任务视频以 30 fps 编码，播放时间不等于仿真物理时间。

训练时输入和目标如何对齐，还需要读数据转换脚本；不要直接把同一行中的图像和关节目标当成“预测下一步”的定义。

## 部署记录：环境与下载

下列为本次已验证部署使用的步骤；每阶段日志和今日进度记录实际结果。要求已有 Linux NVIDIA 驱动、Python 3.10、Git、g++、ffmpeg 和 uv。全部在项目根目录操作，下载与编译占用数 GiB 以上空间。

```bash
# 本地已有 RoboTwin 则检查版本，不必重复克隆。
git clone https://github.com/RoboTwin-Platform/RoboTwin.git RoboTwin
git -C RoboTwin checkout 13c3c47ff4312dd62484bcd51be034af55c062d1
# 仅在新检出的上游版本应用一次；本机已应用。
git -C RoboTwin apply ../2026-10-20/robotwin-minimal-assets.patch
python3 scripts/prepare_robotwin_assets.py

tools/uv-x86_64-unknown-linux-gnu/uv venv .venv-robotwin --python tools/python/cpython-3.10.22-linux-x86_64-gnu/bin/python3.10
source scripts/robotwin_env.sh
uv_bin="$VLA_ROOT/tools/uv-x86_64-unknown-linux-gnu/uv"
"$uv_bin" pip install --python .venv-robotwin/bin/python torch==2.7.1 --index-url https://download.pytorch.org/whl/cu128
"$uv_bin" pip install --python .venv-robotwin/bin/python -r 2026-10-20/robotwin-runtime.in 'setuptools_scm>=6.2' 'yourdfpy>=0.0.53' numpy-quaternion tqdm importlib_resources scikit-image six lxml
python scripts/torch_gpu_smoke.py

git clone --branch v0.7.8 --depth 1 https://github.com/NVlabs/curobo.git RoboTwin/envs/curobo
"$uv_bin" pip install --python .venv-robotwin/bin/python -e RoboTwin/envs/curobo --no-build-isolation
```

项目内 CUDA 编译器来自 NVIDIA CUDA 12.8.1 官方 redistributable，下载路径与 SHA256 见 `cuda-redist.json`。驱动显示的 CUDA 13.2 与这个用于编译的 12.8 工具链是不同概念。

不启用 pointcloud，因此暂不安装 PyTorch3D 的点云采样模块；不自动生成 API 语言描述，任务的专家动作逻辑仍使用上游实现。最小资产补丁 `robotwin-minimal-assets.patch` 将杂物数据库改为需要时加载：clean 任务不再因导入杂物辅助模块而要求完整物体包。启用杂物后仍需真实资产；不构造空数据库，也不修改任务动作或成功条件。当前不是未经修改的上游工作树。

## 专家示范与数据检查命令

仅在 GPU 计算测试和 CuRobo 编译通过后运行：

```bash
source scripts/robotwin_env.sh
# 新目录避免覆盖第一次实验。最多尝试 5 个种子；外部限制 15 分钟。
timeout 900 python -u scripts/run_expert_episode.py --output-dir 2026-10-20/reproduce_expert --max-attempts 5
python scripts/inspect_episode.py 2026-10-20/reproduce_expert/data/episode0.hdf5 --grid-video
```

采集分两步：第一遍规划并保存成功轨迹；第二遍重建相同种子的场景、回放该轨迹、保存观测。两遍都检查成功条件。脚本省略官方采集脚本最后的批量语言描述生成；不调用语言模型 API。

本机旧版 SAPIEN 的 OIDN 去噪器报不支持 CUDA 设备，采集脚本的 `TaskWithCompatibleRenderer.setup_scene()` 仅将去噪设为 none；保留光线追踪、32 samples per pixel、物理与任务动作。视觉结果与上游默认去噪设置有差异；这是教学复现，不是官方指标评测。

`result.json` 的 `expert_task_pass` 必须为 true，且视频与 HDF5 文件存在，才算本次专家链路通过。若退出码非零，先读日志或 `result.json` 的错误；不要因为有视频或部分数据就认定任务成功。
